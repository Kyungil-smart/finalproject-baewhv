# 기업협약 HCD 프로젝트 룰

## 팀 작업 규칙
- 큰 목표는 깃허브 마일스톤으로 관리, 세부 목표는 WBS에 작성할 것.
- 다른사람의 작업물을 건드려야 할 경우, Issue탭에 Suggest를 이용할 것.
- 다른사람과 연동작업등이 필요하다면 팀장에게 보고 후 진행.
- 시간 약속을 지킵시다. 못지킬거같으면 미리 말하는것도 중요합니다.
  - 특히 작업 완료 기간을 못지킬거같다면 더더욱...
- 내부 회의는 간략하게 2회 진행합니다.
  - 오전 회의 10:00.
    - 컨디션 체크하여 WBS 건강탭에 체크해둘것.
    - WBS에 오늘 뭐할지 작성할 것.
    - 작성한 것을 기준으로 간단하게 회의.
  - 오후 회의 17:40
    - 공지에 뜨는 회고 작성하며 금일 정리.
    - 회고 작성을 기준으로 오늘 뭐했는지, 문제가 있는지 체크.
  - 한 작업이 너무 오래걸린다면 지체없이 보고합니다.

## Github 사용 규칙
### 커밋 규칙
- 작업 단위를 지킬 것.
  - 너무 많은 것을 한꺼번에 올리지 말것.
  - 에러가 나지 않는 단위로 올릴것.

- 브랜치 규칙상으로 Main 및 Develope에는 직접 올리지는 못함.

### 커밋 메시지 규칙
- 대괄호만 지키고 이왕이면 대문자로.
- 
  - [ADD] : 새로운 기능 추가.
  - [UPDATE] : 기능 변경.
  - [FIX] : 버그 수정.
  - [DEL] : 파일 삭제.
  - [MOVE] : 파일 이동 (파일 및 폴더 정리 시 사용할 것)
  - [DOCS] : 문서 수정 시

### 브랜치 생성 규칙
- 브랜치 풀 리퀘스트 이후 작업은 새 브렌치를 팔것.
- 브랜치 네이밍은 "작업명"_"작업자 이니셜"' 형식을 기본으로 설정하여 어떠한 작업인지, 누가 작업하는지 파악하기 쉽게 작성할것.
  - 기능명 규칙
    - PlayerMovement_bjm  : 플레이어 움직임 작업
    - Featplayer_bjm : 플레이어 기능 개발

### Pull Request 병합 규칙
- 에러가 나지 않는 상황에서 올릴 것.
- 병합하기 전 반드시 디스코드에 공지.
- 팀장에게 디스코드로 병합 요청 (@Annotation 사용)
- 충돌이 있어도 일단 리퀘스트로 올리고 상황 얘기할 것.

### Github Issues
- 제안사항이 있다면 [기능 제안] 항목으로 작성.
- 버그 발생 시 [버그 리포트] 항목으로 작성.

## Unity 규칙

### Unity 프로젝트 폴더 구조
- 각 요소에 맞는 폴더 Scenes, Prefabs, Auido, Resources, Sprites 등등 미리 생성
- _Imports 폴더에 공유되지 말아야할 리소스를 업로드할 것.
  - 어지간한 이미지파일, 사운드파일 여기에 다 넣을것.
  - 작업자 단위로 번들 관리. 추후 폴더 내부 구조가 바뀌어 삭제후 재설치를 위해.
    - ex) _Imports/bjm/...
    - ex) _Imports/kyh/...


## 코드 규칙
### 중요 객체 명칭
- 열거형 : E****            
  - ex) ECount
- 인터페이스 : I****        
  - ex) IAttackable
- 추상 클래스 : Base****    
  - ex) BaseMonster
### 변수명 규칙
- camelCase, PascalCase 등이 있지만 Unity상에서 지정된 규칙으로 따를것!
  - 변수명에 밑줄만 안뜨게 해주세요!

## 설계 규칙
- 입력
  - New Input System을 사용.
- 동적 로딩
  - Addressable 사용.
  - Resources 사용 금지.
- 탐색을 최소화할 것.
  - GetComponentsInChildren 등등...
  - FindAnyObject 등등...
- 레이어 및 태그는 신중히 사용할 것.
- **태그 및 레이어 변경사항이 보이면 찾아갑니다.**

### 씬 규칙
- Scenes              -> Init, Lobby, Title
  - Scenes/Stage      -> stage 별로 필요한 데이터 설정
  - Scenes/Test       -> build 씬 목록에 들어가지 않을 테스트 씬들.
- 씬 내부를 최대한 프리펩화.
  - 프리펩 내 프리펩 구조는 지양할것.
  - 프리펩 내 프리펩 구조가 꼭 필요하다면 동적 로딩.
  - **풀 리퀘스트에 씬 변경사항이 보이면 찾아갑니다.**
  - 초기 씬에서 진입하지 않아도 테스트는 가능하게 만들어볼것.
